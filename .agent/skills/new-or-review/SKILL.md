# 博客写作与审稿

这个 skill 负责两类任务：

- **新建**：从主题到终稿，走完整的流程
- **审阅**：对现有文章做技术审校、风格审校和 AI 痕迹 / author-fit 检查

## 核心联动机制

### 与私有作者画像的联动

如果有可用的私有作者画像，写作前先读认知框架，理解底层假设，再决定文章推进方式。没有画像或材料不足时，先向作者确认，不要补造背景。

**联动流程**：

1. 如果可用，读取私有作者画像
2. 根据文章主题，确定哪个认知维度最相关：
   - 技术学习文章 → 知识观（文章要展示认知过程）
   - 系统设计文章 → 工程观（文章要展示 trade-off）
   - 经历复盘文章 → 成长观（文章要展示认知螺旋）
   - 所有文章 → 表达观（文章要有锚点，允许留白）
3. 根据认知框架决定文章结构：
   - 知识观 → 结构是”误解 → 撞墙 → 修正”，不是”定义 → 特性 → 应用”
   - 表达观 → 开头用问题或场景切入，结尾允许没讲满
   - 工程观 → 系统设计要展示 trade-off 思考过程
   - 成长观 → 翻车经历要保留，不能删成完美阶梯
4. 调用具体经历做证据 → 每段经历要关联认知转折
5. 写作完成后检查：是否体现了认知框架？还是只在引用事迹？

**关键原则**：

- 引用事迹 ≠ 理解认知框架
- “他在 OceanBase 做过可观测平台” → 只引用事迹
- “他在 OceanBase 因为需求边界模糊翻车，此后对'需求边界澄清'有体感” → 理解认知框架

### 与 humanizer-zh 的联动

改写时先读表达观，理解为什么不喜欢某些表达：

- 删掉”回头看” → 因为成长感不该硬提醒
- 删掉”本质上” → 因为不该假装全知
- 保留作者语气 → 因为情绪可以有，但不能表演

## 使用顺序

### 新建文章

1. 如果可用，读取私有作者画像
2. 再读作者提供的经历材料
3. 如果主题涉及具体项目，再读相关经历或简历材料
4. 再读 `references/new-post-workflow.md`
5. 根据文章类型按需读 `references/article-types.md`
6. 如果用户明确要求模仿某种文风，读 `references/style-extraction-method.md` 和用户提供的样本
7. 首稿完成后读 `references/review-and-revise.md`
8. 如果有明显套话或模板味，读 `../humanizer-zh/references/anti-patterns.md`
9. 如果本轮暴露了新的稳定偏好或素材，提出回写私有作者画像的建议，经用户确认后再回写

### 审阅现有文章

1. 如果可用，读取私有作者画像
2. 必要时读取作者提供的经历材料
3. 再读 `references/review-and-revise.md`
4. 若问题集中在模板味、AI 味、结尾过度收束，再读 `../humanizer-zh/references/anti-patterns.md`
5. 如果用户要求模仿某个作者或样本，先取得用户提供的样本，再读 `references/style-extraction-method.md`
6. 如果用户真实改稿暴露了新的稳定偏好，提出回写私有作者画像的建议，经用户确认后再回写

### 提取或学习文风

1. 先读 `references/style-extraction-method.md`
2. 如果要重新提取或更新卡片，先取得用户提供的原始样本
3. 再读已有的通用方法说明
4. 输出时区分：
   - `可观察特征`
   - `推测性偏好`
   - `可训练动作`
5. 不把样本的主题、口头禅、格式习惯误当成全部文风

## 不可违反的规则

1. 不让 AI 一步到位写完整篇文章。
2. 内置脚本只负责提供可疑信号，不负责代写终稿，也不替代审稿判断。
3. 修订时只改命中的段落，不整篇重写。
4. 自动回环最多 2 到 3 轮，之后交给人工裁决。
5. 只要存在认知边界、材料缺口、叙述方式不确定，先访谈，不硬写。
5.1. 任何时候，只要你对写出来的东西有一丝「这可能不是作者真正相信的」的感觉，必须停下来问，不要继续。
6. 篇级句法限额要当硬约束处理：
   - “不是……而是……”最多 1 次（默认目标 0 次）
   - “回头看”最多 1 次（默认目标 0 次）
   - “后来才（发现/意识到/明白）”最多 2 次
   - “按我现在的理解””我更愿意把……理解成”最多 1 次
   超出即按模板化写作处理并优先改掉。

## 程序化审稿脚本

脚本路径：`scripts/review_signals.py`（相对当前 skill 目录）

它是轻量辅助工具，不是独立判定系统。优先用于审阅已有文章、首稿后的 review、以及用户明确要求“降 AI 味”“查模板感”的场景。

脚本只负责：

- 标记可能的 AI 痕迹、模板化表达、节奏问题和硬证据缺失
- 给出段落级位置、命中词和修改方向
- 帮助 review 更快定位问题

脚本不负责：

- 定义本 skill 的写作 prompt
- 直接产出最终文章
- 判断整篇文章是否像作者本人
- 决定整篇文章的最终取舍

使用方式：

```bash
python .agent/skills/new-or-review/scripts/review_signals.py path/to/article.md
```

把脚本输出当成 `signals`，再结合文章材料、可用的私有作者画像和人工审稿判断生成 revision plan。脚本没有命中的地方不代表没有问题；脚本命中的地方也不代表必须修改。

## 输出原则

- 首先报告证据和判断，不先端漂亮结论
- 允许局部不确定，但不能把不确定写成事实
- 优先保留作者自己的材料、火气、犹豫和认知来路
- 需要回访作者时，明确列出少量关键问题，不铺满
